# 工业轴承检测场景 PER-DDPG 技术方案文档设计

## 目标

基于《关于开会时提出的问题》和《2026.7.5(2)》两份文档，并结合论文第 3 章 PER-DDPG 算法，形成一份可独立阅读的中文 Word 正式技术方案。文档将原工业检测表述统一落到滚动轴承状态监测场景，并明确删除雾层。

## 系统边界

- 保留：轴承传感器、一体化采集发送器、MQTT Broker、调度器、多个异构边缘节点、云端。
- 删除：所有雾节点、雾层转发、边缘至雾的链路、雾节点数量实验，以及把雾节点作为动作候选的表述。
- 新拓扑：采集发送端 -> MQTT Broker/调度器 -> 边缘节点群 -> 必要时云端。
- 调度器不负责故障诊断，只负责根据任务、节点资源、网络状态和检测反馈决定任务去向、资源比例、是否复核及是否上云。

## 内容结构

1. 文档目的与结论摘要。
2. 两份源文档的内容分析、互补关系及尚未统一的问题。
3. PER-DDPG 论文算法与轴承场景的对应关系。
4. 无雾层工业轴承检测系统架构与角色边界。
5. 数据采集、50 ms 微批量、200 ms 分析窗口和 MQTT 接口流程。
6. 将一次轴承检测任务拆分为 DAG 子任务，并用算法 3.1 生成 `List_seq`。
7. 用算法 3.2 的 PER-DDPG 选择边缘/云节点并分配连续 CPU 资源比例。
8. 单节点初检、条件触发复核、冲突上云、弱网自治和结果闭环的端到端流程。
9. 当前问题、原因、风险、解决方案及验证指标。
10. 实施边界和结论。

## 算法改写原则

- 保留论文的两阶段思想：先基于 DAG 优先级与紧迫性排序，再用 PER-DDPG 决定节点和资源比例。
- 无雾层动作候选改为“当前可用边缘节点集合 + 云端”，不声称这是论文原公式的原样复现，而明确标注为面向轴承场景的结构适配。
- 状态至少覆盖当前任务特征、各边缘节点和云端剩余计算资源、采集端到候选节点的通信条件。
- 奖励核心保持最小化总完成时间；置信度、复核冲突和业务安全规则用于控制流程分支，不擅自混入论文奖励函数。
- `List_seq` 不是全局最优证明，而是满足依赖约束的启发式优先序列；强化学习仍通过跨回合交互学习节点与资源策略。
- 第一次决策只是当前策略的一次输出，不代表第一次即得到最优方案。

## 文档形态

- 输出为中文 `.docx` 正式技术报告。
- 采用 `standard_business_brief` 视觉预设和 `memo_masthead` 首页结构。
- 使用清晰的标题层级、少量真正用于对比的表格、编号流程和必要的重点提示。
- 不修改两份源文档，生成独立成品。

## 验收标准

- 文档中不出现任何作为实际系统组成部分的雾节点或雾层。
- 轴承数据参数与源文档一致：16 kHz、4 ms/64 点、50 ms/800 点、200 ms/3200 点。
- 清楚区分任务排序、节点与资源决策、检测推理、复核和上云五类职责。
- 明确解释 PER-DDPG 为什么仍需要训练，以及算法在当前场景中的适用边界。
- 包含完整工业流程、问题清单、对应解决方案和可验证指标。
- Word 文档成功渲染，所有页面无文字截断、重叠、表格溢出或异常空白。
